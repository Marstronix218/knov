# Revenue source setup

Connectors perform read-only, explicitly requested imports into a selected real project. They never send email, post Slack messages, import an entire Slack workspace, or run instructions found in source content. Demo projects cannot receive live connector data. Credentials (including the Gmail refresh token and OAuth client details), account identity, approved range/query/channels, last-sync time and the Gmail sync watermark are held in macOS Keychain (`com.knov.revenue.connectors`), separate from AI provider credentials. Secrets are never returned by IPC.

## Gmail

Connect from **Sources → Email & chat → Gmail**. The card walks through three steps:

1. **Create a Google sign-in for Knov (one time).** Enable the Gmail API in a Google Cloud project, configure its OAuth consent screen (External, Testing) and add your Gmail address as a test user, then create an OAuth client of type **Desktop app**. Public distribution of `gmail.readonly` may require Google's restricted-scope verification; for your own account, Testing mode is enough. Knov ships no Google credentials of its own.
2. **Choose what Knov may read.** Enter the Desktop client ID (`installed.client_id` in the downloaded credentials JSON) and, if Google shows one, its client secret. Pick a Gmail search (default `newer_than:90d`; narrow it to one client with, for example, `from:@theirdomain.com`), a date range (default: the last 90 days, midnight UTC boundaries, at most 366 days) and an import limit of 1–100 messages, and tick the read-only authorization box.
3. **Sign in with Google.** Knov opens the system browser with account selection and consent, a random IPv4 loopback port, state validation, S256 PKCE, `access_type=offline` and forced consent, so Google returns a refresh token. The card shows progress while the browser is open; consent times out after 180 seconds.

Knov verifies the granted scopes against Google (`gmail.readonly` only; broader Gmail/mail scopes are rejected) and reads the account address. The access token, refresh token, expiry, client ID and optional client secret are stored together in the Gmail Keychain entry and never returned over IPC. The client secret is sent only in HTTPS form bodies to Google's token endpoint (code exchange and refresh), never in a browser URL, and is bounded to 8,192 bytes.

**Durable sign-in.** On each sync, if the access token has expired or expires within 60 seconds, Knov renews it at `https://oauth2.googleapis.com/token` with `grant_type=refresh_token` and saves the new token in Keychain. If Google rejects the refresh (revoked, expired, or the client changed) or no refresh token was issued, sync fails with "Gmail sign-in expired and cannot be renewed; reconnect Gmail in Sources". Status does not refresh, because it is a local Keychain read.

**Incremental sync.** The approved search and date range remain the authorization boundary on every sync. After a sync that was not truncated, Knov stores a watermark (the newest imported message's `internalDate`) in the credential; later syncs add `after:<watermark seconds>` to the query, skip messages at or before the watermark, and so fetch only new mail inside the approved range. A watermark older than the approved start never widens the range. A truncated sync (limit reached) does not advance the watermark, because Gmail lists newest first and advancing would skip older unimported mail; raise the limit or narrow the dates instead. Changing the scope, deleting imported Gmail content, or reconnecting resets the watermark, so the whole approved range is read again; stable message references keep repeated imports deduplicated. The sync result reports `incremental: true` when a watermark was applied.

**Advanced: access token.** The card's advanced section still accepts an already authorized `gmail.readonly` access token. Such a token is not renewed; reconnect when it expires.

Sync imports subject, From/To/Cc, date, thread/message IDs and plain-text MIME bodies. Attachments, HTML-only bodies, external linked pages and tracking content are not fetched. The desktop flow is macOS-only.

References: [Google installed-app OAuth and PKCE](https://developers.google.com/identity/protocols/oauth2/native-app), [refreshing an access token](https://developers.google.com/identity/protocols/oauth2/native-app#offline), [Gmail list/query API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list), [Gmail search operators](https://support.google.com/mail/answer/7190), [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes).

## Slack

Slack requires an HTTPS redirect URL, and Knov has no hosted exchange service. Instead, Slack redirects to a static page on this project's GitHub Pages site, `https://marstronix218.github.io/knov/slack/callback.html` (the Rust constant `SLACK_REDIRECT_URL`, shown in the UI via `revenue_connector_config`). The page (`apps/web/slack/callback.html`) reads `code`, `state` and `error` from its query string, shows the one-time code in a large box with a **Copy code** button and the instruction "Paste this into Knov → Sources → Slack", and shows Slack's `error` if present. It makes no network requests, loads no external scripts or fonts (its CSP is `default-src 'none'` plus inline style/script), sends no referrer, renders values as text only, and removes the query string from browser history once shown. Knov on the Mac performs the code exchange.

Connect from **Sources → Email & chat → Slack**:

1. **Create a Slack app (one time).** At [api.slack.com/apps](https://api.slack.com/apps), choose Create New App → From scratch and pick your workspace. Under **OAuth & Permissions → Redirect URLs**, add the redirect URL above (the card has a Copy button) and save. Under **User Token Scopes** (not Bot Token Scopes) add `channels:history`, `channels:read`, `groups:history` and `groups:read`. Leave token rotation off; rotating Slack tokens are not renewed by Knov.
2. **Connect.** Enter the app's Client ID and Client Secret (Basic Information), a date range (default: last 90 days) and a limit of 1–100 messages, tick the authorization box, and choose **Open Slack to authorize**. `revenue_slack_oauth_start` stores the client ID, client secret and a random state in the Slack Keychain entry as a *pending* sign-in (no token, expires after 15 minutes), then opens `https://slack.com/oauth/v2/authorize` with `client_id`, `user_scope=channels:history,channels:read,groups:history,groups:read`, `redirect_uri` and `state` in the system browser. A user token is requested because thread replies generally need one. If Slack is already connected, start is refused until you disconnect.
3. **Paste the code.** After **Allow**, copy the code from the callback page into "Paste the code from the browser" and choose **Finish connecting**. `revenue_slack_oauth_complete` checks that a pending sign-in exists, that the state matches the one this UI started and has not expired, exchanges the code at `https://slack.com/api/oauth.v2.access` (client ID, client secret, code, redirect URI), takes `authed_user.access_token` and `authed_user.scope`, rejects broader or missing scopes, verifies the token with `auth.test` (scope header checks as for a pasted token), and saves the verified user token. The client secret is then discarded. Slack's error code, if any, is shown sanitized.
4. **Pick channels.** The connected card lists channels by name with `conversations.list` (`types=public_channel,private_channel` as the granted `channels:read`/`groups:read` scopes allow, `exclude_archived=true`, `limit=200`, at most 5 pages). This listing is read-only and imports nothing. Tick 1–10 channels, adjust dates and limit, and choose **Save selected channels**; `revenue_connector_update_scope` updates the stored scope server-side, so the token never returns to the UI. Without a read scope, the list returns "Listing channels needs the channels:read or groups:read scope; enter channel IDs instead" and the card falls back to typing channel IDs.

Sync reads only the 1–10 selected channels within the selected range. It retrieves channel history with participant IDs, timestamps and parent-thread IDs, and bounded `conversations.replies` pages for discovered parents in the same channel and range. Parent messages older than the approved range are not discovered, so their recent replies may be absent; this is a scoped import, not a workspace or thread archive. You may need to be a member of private channels to read them. Slack enforces token-type, membership, app-distribution and rate limits; failures are shown and no automatic retries broaden the scope. Direct messages, write scopes and other broader scopes are rejected.

**Advanced: paste a token.** The card's advanced section still accepts a Slack token with only those read scopes plus explicit channel IDs (`revenue_connector_connect`).

References: [Slack OAuth v2](https://docs.slack.dev/authentication/installing-with-oauth/), [oauth.v2.access](https://docs.slack.dev/reference/methods/oauth.v2.access/), [conversations.list](https://docs.slack.dev/reference/methods/conversations.list/), [conversations.history](https://docs.slack.dev/reference/methods/conversations.history/), [auth.test](https://docs.slack.dev/reference/methods/auth.test/), [auth.revoke](https://docs.slack.dev/reference/methods/auth.revoke/).

**Not exercised here.** No Google or Slack credentials were available in the development environment, so live consent, code exchange, token refresh, channel listing, remote revocation and actual Keychain behavior have not been run against the real services. Offline tests cover URL construction, state and pending checks, refresh decisions, watermark queries and response parsing. The callback page works only after the GitHub Pages site is published.

## Bounds, retention and disconnect

Each sync uses at most ten pages per selected source/channel and ten pages per discovered thread, a total configured message count, a 20-second HTTP timeout per request, a 2 MB response limit, and 64,000 UTF-8 bytes per imported message, truncated only at complete character boundaries. The time range cannot exceed 366 days. The result explicitly reports truncation. Repeated imports use stable provider/message references so the revenue store can deduplicate them. Each fetched batch is ingested in one database transaction; a later invalid record rolls back earlier inserts and updates in that batch. Sync is manual. Gmail keeps an incremental watermark inside the approved range (see Gmail); Slack re-reads the selected range each time and relies on deduplication.

Disconnect immediately deletes the local Keychain entry. Choosing revoke (the Sources **Disconnect** button always does) also calls the provider revocation endpoint: for Gmail it revokes the refresh token when one is stored (which also revokes its access tokens), otherwise the access token; for Slack it calls `auth.revoke`. A pending Slack sign-in has no token to revoke; remote failure is reported after local disconnection, with provider account settings as recovery. Deleting imported Gmail/Slack evidence invalidates any sync already in flight under the same source lock before database deletion; deletion also clears the Gmail watermark, so a later explicitly initiated sync may import the approved range again using the retained credentials. Disconnect does not delete already imported project evidence. Use revenue evidence deletion or full-data deletion for persisted content; existing retention controls prune retained revenue records. Full-data deletion also removes both connector Keychain entries, but does not remotely revoke provider authorization. Revenue source imports remain local; this connector module makes no AI model requests.

## Contract import

User-selected `.txt`, `.md`, `.markdown`, `.docx`, `.doc`, `.rtf`, `.odt` and text-based `.pdf` files up to 2 MB are read locally. Sources uploads the bytes (the webview cannot see file paths); they are written to a private temporary directory only for extraction and removed afterward. PDF extraction calls Poppler `pdftotext` when installed and otherwise macOS PDFKit through `osascript`; word-processor formats use macOS `textutil`. All extractors run with argument boundaries (no shell), time out after 15 seconds, and their output is capped at 2 MB. Missing extractor, extraction errors, empty/scanned PDF and unsupported formats produce explicit errors. No OCR or fallback invented text is supplied.

## IPC contracts

- `revenue_connector_config()` → `{slackRedirectUrl, slackUserScopes, gmailScope}`.
- `revenue_connector_status({provider})` → `{provider, connected, account, scope, lastSync, pending, watermark}`; provider is `gmail` or `slack`. `pending` is true while a Slack sign-in waits for its code; `watermark` is the Gmail incremental point in Unix seconds.
- `revenue_connector_connect({provider, token, scope, authorized:true})` → status. Scope is `{query, after, before, channels, maxItems}`; times are Unix seconds, `before` exclusive.
- `revenue_gmail_oauth({clientId, clientSecret?:string, scope, authorized:true})` → status after browser consent, with a 180-second consent timeout. Stores the refresh token for renewal.
- `revenue_slack_oauth_start({clientId, clientSecret, scope, authorized:true})` → `{authorizeUrl, state, opened}`. Scope may have no channels yet.
- `revenue_slack_oauth_complete({code, state, authorized:true})` → status.
- `revenue_slack_list_channels()` → `[{id, name, isPrivate, isMember}]`.
- `revenue_connector_update_scope({provider, scope, authorized:true})` → status; replaces the approved scope without re-sending a token and resets the Gmail watermark.
- `revenue_connector_sync({provider, projectId})` → `{imported, truncated, incremental}`.
- `revenue_connector_disconnect({provider, revoke})` → void (or explicit remote-revocation failure after local disconnection).
- `revenue_extract_upload({fileName, dataBase64})` → `{title, text}`. Sources calls this for each chosen file and shows the extracted text in an editable preview for review before import; only the reviewed text is passed to `revenue_import_agreement`. Nothing is stored until the import. `revenue_extract_document({path, authorized:true})` is the path-based equivalent for callers outside the webview.

Focused offline tests cover explicit authorization, empty/oversized scope, selected channel IDs, rejection of write permissions and direct messages, Slack authorize URL construction, state and pending-credential checks, Gmail offline-access URL, refresh-needed decisions, `after:` watermark queries, channel-list parsing and missing-scope errors, literal prompt-injection text, and document validation. Live authorization, remote revocation and actual Keychain behavior require manual verification on an authorized macOS account. Core revenue tests cover retained evidence deletion and retention separately.
